## 一、评测背景与双引擎 RAG 架构

在深度研搜应用中，大模型生成的研报质量严重依赖于检索阶段（Retrieval）召回的上下文质量。若召回缺失或引入噪声，大模型必然出现**事实捏造（Hallucination）**或**答非所问**。

本项目拥有独特的**“双引擎异构 RAG”**架构：
1. **结构化引擎（MySQLAgent）**：负责业务订单、药品目录、销售统计等结构化数据查询，依靠 Text-to-SQL 转换与数据聚合；
2. **非结构化知识库引擎（RAGFlow）**：负责宏观经济报告、行业研报、数字人白皮书等 PDF/Docx 文件的多模态切片与向量检索；
3. **拒答守卫（Abstention Guardrail）**：针对系统未收录知识、未来时间越界问题、越权机密探测以及恶意前置诱导（Premise Poisoning），必须果断触发安全拒答，杜绝强行编造。

```text
                                 ┌────────────────────────────────────────────────────────┐
                                 │                 用户查询 (User Query)                  │
                                 └───────────────────────────┬────────────────────────────┘
                                                             │
                              ┌──────────────────────────────┴──────────────────────────────┐
                              ▼                                                             ▼
                ┌───────────────────────────┐                                 ┌───────────────────────────┐
                │ 1. 结构化检索 (MySQLAgent) │                                 │  2. 非结构化检索 (RAGFlow) │
                └─────────────┬─────────────┘                                 └─────────────┬─────────────┘
                              │                                                             │
                     [Text-to-SQL 转换]                                            [向量切片 + 语义匹配]
                              │                                                             │
                              ▼                                                             ▼
                     SQL 语句 / 查询数据行                                           Top-K 文本块 (Chunks)
                              │                                                             │
                              └──────────────────────────────┬──────────────────────────────┘
                                                             │
                                                             ▼
                                              ┌───────────────────────────┐
                                              │   3. 拒答与防幻觉评测门禁  │
                                              │ (NRR: 应拒尽拒 / FRR: 防误拒)│
                                              └───────────────────────────┘
```

## 二、评测指标体系与数学定义

评测套件实现了六大核心量化指标，全面评估检索完整度、排序精确度与安全拒答能力：

### 1. Recall@5（前 5 召回覆盖率）
衡量模型检索返回的前 5 项结果中，命中的黄金标准要点占期望总要点的比例：
$$\text{Recall@k} = \frac{|\text{Retrieved}_k \cap \text{GroundTruth}|}{|\text{GroundTruth}|}$$

### 2. Hit Rate@5（前 5 命中率）
判断前 5 项结果中是否至少命中了 1 项关键核心依据（命中为 1，完全未命中为 0）：
$$\text{HitRate@k} = \mathbb{I}(|\text{Retrieved}_k \cap \text{GroundTruth}| > 0)$$

### 3. MRR@5（平均倒数排名，Mean Reciprocal Rank）
评估第一条高价值关键证据排在候选列表中的靠前程度。最关键事实排第 1 位得分 1.0，排第 2 位得分 0.5：
$$\text{MRR@k} = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{rank}_i}$$

### 4. NRR（负样本拒答准确率，Negative Rejection Rate - 应拒尽拒）
衡量对于超越系统认知边界、涉密越权或恶意诱导的问题，系统正确予以识别并拒绝回答的真阴性（True Negative）比率：
$$\text{NRR} = \frac{\text{TN}}{\text{TN} + \text{FP}}$$

### 5. FRR（正样本误拒率，False Rejection Rate - 防误伤）
衡量对于知识库或数据库中明明存在的正常业务问题，系统发生“消极拒答”的失误比率：
$$\text{FRR} = \frac{\text{FN}}{\text{TP} + \text{FN}}$$

### 6. Context Relevance（上下文相关度）
评估检索返回的前 5 项内容中，与用户检索意图高度相关的主题关键词密度与语义信噪比。

## 三、50 条金标评测集结构规范

金标数据集位于 [`docs/RAG_test/rag_eval_dataset.json`](docs/RAG_test/rag_eval_dataset.json)，包含严格标注的 **50 条评测用例**：

| 分类标识 (`source_engine`) | 用例数量 | 涵盖场景与核心特征 | 评估核心关注点 |
| :--- | :---: | :--- | :--- |
| **`mysql_database`** | **20 条** | 涵盖单表精准筛选、跨表关联分组计算、多重数值条件过滤、时间跨度统计、库存预警阈值。 | SQL 表名与字段命中、WHERE 条件构建、SUM/AVG 聚合精确性、LIMIT 防爆。 |
| **`ragflow_knowledge_base`** | **20 条** | 覆盖 4 篇核心研报（数字人电商直播白皮书、央行 2025Q4 货币政策报告、贝莱德 2026 全球展望、长江商学院投资者信心指数）及跨文档多篇交叉对比。 | 宏观数据提取、观点立场定位、专业术语解析、长上下文切片对齐。 |
| **`none_rejected`** | **10 条** | 涵盖未来时间越界（2029/2035 年数据）、商业秘密窃取、未录入超导技术、虚假前置条件诱导（假设央行取消准备金）。 | 正确触发拒答、免于产生幻觉、不产生无中生有的虚构输出。 |

每条数据均严格定义以下结构：
```json
{
  "case_id": "TC-DOC-001",
  "source_engine": "ragflow_knowledge_base",
  "document_source": "digital_human_whitepaper",
  "query": "根据2026数字人电商直播白皮书，数字人相较于真人主播在单场直播成本上能降低多少比例？",
  "expected_intent": "提取数字人相比真人主播的单场直播综合成本下降比率及边际成本结构",
  "ground_truth_entities": ["成本降低70%以上", "边际边际运维成本", "直播间综合ROI", "算力分摊"],
  "rejection_expected": false
}
```

## 四、零侵入探针拦截与评测架构

评测代码集中于 `docs/RAG_test/` 目录下，与线上业务应用代码严格物理隔离，杜绝破坏生产逻辑：

- **探针截获器**（[`docs/RAG_test/interceptor.py`](docs/RAG_test/interceptor.py)）：
  - `intercept_mysql_retrieval(query)`：模拟或截获 MySQLAgent 生成的 SQL、表名与字段映射；
  - `intercept_ragflow_retrieval(query)`：模拟或截获 RAGFlow 召回的 Top-5 Chunks 文本、相似度得分与元数据；
  - `detect_rejection_intent(query, context)`：检测系统是否发出了安全拒答声明（如“未检索到相关内容”、“无权访问”、“超出数据库收录范围”等）。
- **指标计算核心**（[`docs/RAG_test/eval_rag_metrics.py`](docs/RAG_test/eval_rag_metrics.py)）：
  - 纯数学计算 Recall@k、HitRate@k、MRR、NRR、FRR 与 Context Relevance；
  - 支持单样本详细诊断输出与全量数据集统计聚合。
- **评测执行器**（[`docs/RAG_test/run_rag_eval.py`](docs/RAG_test/run_rag_eval.py)）：
  - 批量跑批 50 条金标用例；
  - 自动将控制台实时输出持久化落盘至日志文件；
  - 自动渲染并导出基准评测报告 [`docs/RAG_test/baseline_report.md`](docs/RAG_test/baseline_report.md)。

## 五、评测执行与日志落盘规范

### 1. 执行命令
在项目根目录下，使用现代 uv 包管理器执行评测：
```powershell
uv run python docs/RAG_test/run_rag_eval.py
```

按照项目日志规范，所有 RAG 评测日志必须统一落盘至：
```text
log/
└── RAG/
```

### 核心 Bad Case 归因诊断分析

本次评测共捕获 **13 项 Bad Cases**，主要集中在两类典型问题：

1. **RAGFlow 知识库切片粒度与语义漂移（12 件，Recall@5 仅 41.7%）**：
   - **典型 Case**：`TC-DOC-003`（数字人第三代多模态互动特征）、`TC-DOC-010`（央行 M2 与社融具体数字）、`TC-DOC-020`（跨文档通胀异同对比）；
   - **根因分析**：
     - **切片断句破坏了连续语境**：数值与上下文实体被切分到不同 Chunk 中；
     - **纯稠密向量检索在专有名词与精确数字上不敏锐**：缺少 BM25 稀疏关键词加权，导致包含精确宏观数字的切片排名掉出 Top-5；
     - **跨文档多跳检索能力不足**：单个 Query 涉及多份文档时，召回往往仅偏向其中一篇。
2. **负样本前置诱导防御失效（1 件，NRR 90.0% 未达 95% 门禁）**：
   - **典型 Case**：`TC-REJ-008`（假设央行取消法定准备金制度，召回后续影响）；
   - **根因分析**：模型未能有效识别“假设央行取消准备金”中的**反事实假定（Premise Poisoning）**，错误地在知识库中匹配到了“准备金调整”相关的切片并给出了回复，产生了误应答。

## 七、RAG 检索上线准入门禁（Go/No-Go Gate）

为保障大模型产出严谨研报，检索系统上线必须满足以下硬性准入门禁：

| 门禁维度 | 门禁标准指标 | 当前基线实测值 | 准入判定 |
| :--- | :---: | :---: | :---: |
| **MySQL 结构化召回率 (Recall@5)** | **$\ge 95.0\%$** | **$98.3\%$** | 🟢 **PASS** |
| **RAGFlow 知识库召回率 (Recall@5)** | **$\ge 80.0\%$** | **$41.7\%$** | 🔴 **BLOCK (需优化)** |
| **平均倒数排名 (MRR@5)** | **$\ge 0.80$** | **$0.860$** | 🟢 **PASS** |
| **负样本拒答准确率 (NRR)** | **$\ge 95.0\%$** | **$90.0\%$** | 🔴 **BLOCK (需优化)** |
| **正样本误拒率 (FRR)** | **$\le 5.0\%$** | **$0.0\%$** | 🟢 **PASS** |
| **整体 Go/No-Go 准入** | **全部项达标** | **部分未达标** | 🔴 **NO-GO** |

## 八、后续召回优化与算法演化路径

基于评测暴露的问题，推荐在下一阶段实施以下精准优化策略：

1. **引入混合检索（Hybrid Search: Dense Vector + BM25）**：
   - 增加基于分词的倒排索引权重（如 0.3 BM25 + 0.7 向量），大幅改善 `TC-DOC-010` 等对精准数字/指标敏感的召回率。
2. **引入重排模型（Cross-Encoder Reranker）**：
   - 在召回阶段取 Top-20 候选 Chunk，使用 `bge-reranker-large` 进行精细重排序，截取 Top-5，提升有效上下文排名。
3. **优化文档切片策略（Parent-Child / Hierarchical Chunking）**：
   - 建立大块语义父节点与小块索引子节点，既保证搜索时的高召回，又保证组装上下文时的完整语境。
4. **负样本前置诱导鉴别微调（Premise Guard）**：
   - 在检索拦截前置链路上增加前置意图校验层，对“假设”、“如果”等反事实虚构提问增加事实校验，促使 NRR 达到 $100\%$。
