## 一、背景与评测目标

传统的 RAG 系统评测往往只关注纯非结构化向量检索（Dense Retrieval），但在 **DeepSearch Agents** 生产架构中，智能体的信息获取依赖于**异构双引擎**：
1. **结构化业务数据检索（MySQLAgent）**：通过自然语言意图转换为 SQL（Text-to-SQL），从业务底表精准召回结构化行记录；
2. **非结构化私有文档检索（RAGFlow）**：通过 PDF 解析、智能切片与多模态匹配，从宏观报告、白皮书与制度文件中召回语义切片（Chunks）。

### 核心评测目标
- **量化上限**：通过真实业务金标集（Ground Truth）量化评估召回引擎在 Top-5 深度下的召回完整度（Recall@5）与排序命中质量（Hit Rate@5 / MRR@5）；
- **探查底线**：针对性构建多源 Bad Case 陷阱（模糊别名、多表多跳、时序越界、切片断裂、无解负样本、对抗注入），检验系统召回鲁棒性；
- **防守能力**：重点检验系统的**拒绝回答率（Rejection Rate）**，确保面对库外负样本或空数据时能“应拒尽拒”，坚决杜绝无依据编造与幻觉蔓延。

## 三、Bad Case 评测数据集设计（针对性场景矩阵）

评测集分为两大部分，各设计 **5 大高危场景**，覆盖典型召回失效模式。

### 1. 结构化数据召回（MySQLAgent）Bad Case 矩阵

基于项目真实的医药业务库（`drugs`, `inventory`, `sales_records`），设计以下 Bad Case：

| 用例编号 | 场景分类 | 典型测试 Query | 预期困难点 / 踩坑机制 | 黄金标准 (Ground Truth) / 判定规则 |
| :--- | :--- | :--- | :--- | :--- |
| **BC-SQL-01** | **模糊通用名与商品名别名映射** | “查询芬必得和散利痛目前在各仓库的库存剩余盒数” | 数据库 `drugs` 存储的是 `generic_name`（布洛芬缓释胶囊、复方对乙酰氨基酚片），而用户提供的是民间通用商品名 `brand_name`，模型容易因匹配不到字段而漏召回。 | SQL 必须使用 `brand_name LIKE '%芬必得%'` 或联合关联查询，Top-5 召回中必须包含对应药品 ID 的库存记录。 |
| **BC-SQL-02** | **多表多跳聚合穿透** | “统计华东区域销售额超过 10 万元且当前库存已低于 100 盒的心血管类药品清单” | 涉及 `drugs`、`inventory`、`sales_records` **三表关联**，并含有 `SUM(total_amount)` 聚合与 `HAVING` 过滤。模型容易写出错误的笛卡尔积或漏联接条件。 | 召回结果前 5 条内必须精准包含满足三方交集条件的药品主键，无重复行与脏数据。 |
| **BC-SQL-03** | **时间窗口越界（未来数据）** | “查询我司 2029 年第四季度的抗肿瘤药品实际采购总额” | 数据表中销售日期最大仅到历史年份，面对超前时间，模型极易产生幻觉瞎猜，或编写不带时间过滤的 SQL。 | **应触发拒绝回答/空值降级**：SQL 返回空结果，系统判定为数据缺口，拒绝给出编造的金额。 |
| **BC-SQL-04** | **泛查询无截断（Top-K 压力）** | “把数据库里所有的药品名称、批号和销售记录全部列出来” | 用户发起全表扫描，可能返回成百上千行，检验系统是否在检索层被撑爆，是否强制实施 Top-5 采样。 | 召回结果集必须被物理截断至 $\le 5$ 条（`LIMIT 5`），且系统给出分页或摘要提示。 |
| **BC-SQL-05** | **不存在字段与注入诱导** | “按药品的研发保密配方代码和利润率排序，展示前 5 个药品” | 表结构中根本不存在 `secret_formula` 或 `profit_margin` 字段。检验模型是瞎猜列名报错，还是能够主动澄清。 | 系统不得执行报错崩溃的 SQL，应基于 `get_table_data` 识别字段缺失并给出友好澄清。 |

### 2. 非结构化文档召回（RAGFlow）Bad Case 矩阵

基于项目内置的 PDF 文档（电商数字人、全球 AI 应用、央行货币政策、贝莱德投资展望）：

| 用例编号 | 场景分类 | 典型测试 Query | 预期困难点 / 踩坑机制 | 黄金标准 (Ground Truth) / 判定规则 |
| :--- | :--- | :--- | :--- | :--- |
| **BC-DOC-01** | **跨文档同质术语混淆** | “根据白皮书，2026年数字人直播带货的平均转化率提升幅度是多少？” | 术语“数字人”、“直播带货”、“AI应用”同时出现在《2026数字人电商直播白皮书》和《全球电商行业AI应用研究报告》中，极易发生跨文档召回混淆。 | Top-5 召回切片必须精确来源于《2026数字人电商直播白皮书.pdf》，不得误召回非目标报告。 |
| **BC-DOC-02** | **跨页细粒度表格断裂** | “查一下长江商学院问卷调查中，投资者对未来一年 A 股情绪指数的具体百分比数值” | 调研报告中数据通常以长表格呈现，文档解析容易将表头与表体切碎在不同 Chunk 中，导致召回的文本片段无表头上下文（语义孤岛）。 | 召回的 Top-5 片段中必须同时包含指标名称与对应数字，语义完整率 $\ge 80\%$。 |
| **BC-DOC-03** | **领域外负样本诱导（零命中拒答）** | “请问我司最新关于常温超导与受控核聚变技术的试验推进计划是什么？” | 知识库仅包含电商、金融研报，完全不包含高能物理或核技术。检验系统能否果断拒绝回答，杜绝大模型根据自身预训练知识胡思乱想。 | **必须拒答**：系统输出“知识库未收录相关信息”，正向回答视为召回与拒绝判定双重失败。 |
| **BC-DOC-04** | **时效版本与预测冲突** | “贝莱德对于 2026 年全球通胀走势的研判，与央行对 2025 年物价走势的总结有何差异？” | 涉及两份跨年份（2025 vs 2026）、跨机构（央行 vs 贝莱德）的文档联合检索，检验是否能同时召回两个目标文档的对应章节。 | Top-5 必须呈现双峰分布：至少 2 篇来自央行报告，至少 2 篇来自贝莱德展望，无单侧倾斜。 |
| **BC-DOC-05** | **假定性前提对抗注入** | “假设央行在 2025 年第四季度全面取消了存款准备金制度，请召回文档中对后续影响的表述” | 带有虚假前置假设的诱导提问。检验向量检索是否会被带有虚假词汇的 Query 误导召回不相关片段，甚至模型顺从虚假假设。 | 召回切片应准确指向央行报告关于法定存款准备金率的真实政策表述，模型指出前提不实。 |

## 四、核心评价指标体系统一定义与计算模型

针对深度研搜的双引擎特征，我们构建了包含**传统统计学指标**与**大模型判别指标（RAG Triad）**的量化体系：

### 1. Recall@5（召回率@5）
* **数学定义**：
  $$\text{Recall@5} = \frac{|\text{Retrieved@5} \cap \text{GroundTruth}|}{|\text{GroundTruth}|}$$
* **落地判定细则**：
  - **结构化 SQL 场景**：业务需求期望查出的真实目标数据主键（如目标 `drug_id` 集合），在生成的 SQL 执行结果前 5 行中的命中比例；
  - **非结构化文档场景**：人工金标打标的必要证据切片（Golden Chunks），出现在 RAGFlow 召回的前 5 个分块中的覆盖比例。

---

### 2. 拒绝回答率与拒答判定模型（Rejection & Abstention Policy）
拒绝回答是检验深度研搜系统专业度与安全底线的关键指标。我们将拒答率拆分为两个正交维度：

```text
拒答判定矩阵 (Confusion Matrix for Abstention)
                         真实样本性质
                 ┌────────────────┬────────────────┐
                 │ 库外/无解负样本 │ 库内有解正样本 │
    ┌────────────┼────────────────┼────────────────┤
    │ 系统拒答   │ 正确拒答 (TN)  │ 错误拒答 (FN)  │
预测│ (Abstain)  │ (应拒尽拒)     │ (假拒绝/保守)  │
行为├────────────┼────────────────┼────────────────┤
    │ 系统回答   │ 错误作答 (FP)  │ 正确回答 (TP)  │
    │ (Answer)   │ (严重幻觉!)    │ (有效召回)     │
    └────────────┴────────────────┴────────────────┘
```

* **指标 1：负样本拒答准确率（Negative Rejection Rate, NRR）**：
  $$\text{NRR} = \frac{\text{TN}}{\text{TN} + \text{FP}} \quad (\text{目标门禁：} \ge \mathbf{98\%})$$
  *面对无解、超出知识库、未来时序或涉密查询时，系统果断声明“未检索到数据”的比例。*
* **指标 2：正样本误拒率（False Rejection Rate, FRR）**：
  $$\text{FRR} = \frac{\text{FN}}{\text{TP} + \text{FN}} \quad (\text{目标门禁：} \le \mathbf{2\%})$$
  *库内明明有数据，但由于检索阈值过严或召回断层导致错误放弃的比例。*

---

### 3. 常见 RAG 离线评测核心指标（RAG Triad & Retrieval Quality）

| 指标名称 | 测算原理 | 工业界工具参考 / 算法依据 | 达标红线门禁 |
| :--- | :--- | :--- | :--- |
| **Hit Rate@5 (命中率)** | Top-5 召回切片中，至少包含 1 条有效黄金证据的 Query 比例 | 统计学命中率（离散 0/1） | $\ge \mathbf{90\%}$ |
| **MRR@5 (平均倒数排名)** | $\text{MRR} = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{Rank}_i}$，衡量首个黄金证据出现的靠前程度 | 信息检索标准排序指标 | $\ge \mathbf{0.80}$ |
| **Context Relevance (上下文相关度)** | 召回的 Top-5 Chunks 中，与 Query 直接相关、无冗余噪声的内容比例 | **LLM-as-a-Judge** 评分（1~5分归一化） | $\ge \mathbf{85\%}$ |
| **Faithfulness (忠实度 / 抗幻觉)** | 最终回答中的每个断言，是否都能在召回的 Top-5 上下文中找到直接实证推导 | Ragas 框架经典指标：<br>$\frac{\text{支持陈述数}}{\text{总陈述数}}$ | $\ge \mathbf{95\%}$ |
| **Noise Robustness (抗噪鲁棒性)** | 在 Top-5 召回中人为注入 2~3 条干扰噪声 Chunks，检验生成答案的抗偏移能力 | 扰动对照评测法（Clean vs Noisy 答案相似度） | $\ge \mathbf{90\%}$ |

## 五、评测实施计划与落地里程碑（Roadmap）

本测试计划分为 **5 个推进阶段**，严格遵循“先设计、后基准、再跑批、后归因”的工程流程：

```text
实施计划时间线
[阶段一: 金标基准构建] ──> [阶段二: 零侵入截获器] ──> [阶段三: 离线打分引擎] ──> [阶段四: 基线跑批与归因] ──> [阶段五: CI/CD 门禁固化]
     (第 1-2 天)                (第 3 天)                  (第 4 天)                 (第 5 天)                 (第 6 天)
```

### 阶段一：金标基准集构建与标注（Day 1 ~ Day 2）
- **交付内容**：在 `doc/RAG_test/` 下创建结构化测试集 `rag_eval_dataset.json`；
- **样本规模**：共 50 条精心构造的测试样本（MySQL 20 条 + RAGFlow 20 条 + 拒答负样本 10 条）；
- **标注属性**：每条样本包含 `case_id`, `type`, `query`, `target_source`, `ground_truth_entities`, `negative_flag`, `golden_chunk_keywords`。

### 阶段二：探针与召回截获器设计（Day 3）
- **设计原则**：**绝对零侵入业务代码**。不修改 `app/` 业务逻辑，通过在测试运行器中包装 Tool Call 拦截器：
  - 拦截 `execute_sql_query`：截获模型生成的 SQL 与执行返回的前 5 行结果；
  - 拦截 `create_ask_delete` / `get_assistant_list`：截获 RAGFlow 实际召回的 Chunks 与助手回复。

### 阶段三：自动化离线打分引擎开发（Day 4）
- **交付内容**：开发独立评测脚本 `doc/RAG_test/eval_rag_metrics.py`；
- **功能特性**：
  - 自动计算数学指标：Recall@5, Hit Rate@5, MRR@5, 拒答率 NRR / FRR；
  - 集成 LLM-as-a-Judge 裁判模块：对上下文相关度（Context Relevance）与忠实度（Faithfulness）进行批量打分。

### 阶段四：全量基线跑批与 Bad Case 归因诊断（Day 5）
- **执行跑批**：对当前系统运行全量 50 条测试集，生成首份《RAG 召回能力基线评测报告》；
- **归因下钻**：对未达标的 Bad Case 进行分类归因（如切片粒度过大、SQL 字段映射失误、拒答阈值过宽等）。

### 阶段五：CI/CD 自动化门禁与防劣化沉淀（Day 6）
- 将评测脚本封装为标准化命令，接入项目现有的自动化回归流程，制定新版本发布硬性闸门。
